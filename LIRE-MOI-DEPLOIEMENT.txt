2) CE QUI A ÉTÉ CORRIGÉ DEPUIS VOTRE DERNIÈRE CAPTURE
---------------------------------------------------------------------
Votre capture s'arrête sur :
     #12 [7/7] COPY db* ./db/  DONE 0.0s
     ===> failed to calculate checksum ...

Cela signifie que la construction ne trouvait pas, dans le dossier envoyé à
Render, les pièces attendues par l'ancienne recette (dont un dossier /docs).

Correctifs apportés :

  1. UN SEUL Dockerfile, À LA RACINE du projet. Il ne copie que ce qui est
     indispensable (backend/package*.json, backend/src, db/) et ne réclame
     plus aucun dossier facultatif. Il ne peut donc plus échouer sur un
     fichier manquant.

  2. LE SERVEUR DÉMARRE EN PREMIER, LA BASE SUIT. Avant, la migration de la
     base passait avant le démarrage : base endormie = service injoignable
     ou « Application exited early ». Maintenant le port s'ouvre en une
     seconde, puis la migration tourne en arrière-plan et se réessaie toute
     seule (3 fois, toutes les 20 s).

  3. PLUS D'ERREUR DE FICHIER INTROUVABLE. Le serveur ne cherche plus un
     dossier /frontend absent : il redirige vers votre site Netlify.

  4. LA FAUTE QUI COUPAIT L'API EST CORRIGÉE (« req is not defined »).
     Une erreur isolée n'arrête plus le service.

  5. LA MIGRATION N'EST PLUS BLOQUANTE : elle vérifie la base en 3 x 4 s,
     ne rejoue pas 29 scripts si la base est déjà à jour, et affiche en
     clair le dossier db/ qu'elle utilise.

3) NOUVEAUTÉ POUR VOUS DIAGNOSTIQUER : /ready
---------------------------------------------------------------------
Ouvrez dans le navigateur :   https://VOTRE-API.onrender.com/ready

   {"pret":true, "base":"connectee", "tables":34, "migration":"terminee"}

  • pret:true      → la base répond et les tables existent : tout va bien.
  • base:injoignable → la base Render dort ou DATABASE_URL est fausse : copiez
                       moi le texte affiché.
  • migration:"reportee" → elle réessaiera seule ; attendez 1 minute.

Et :  https://VOTRE-API.onrender.com/healthz   →  {"ok":true}
      https://VOTRE-API.onrender.com/          →  vous renvoie vers le site

4) LE SEUL POINT QUI A ÉCHOUÉ — À VÉRIFIER AVANT DE RELANCER
---------------------------------------------------------------------
Sur Render, un service Docker a DEUX réglages de dossier :

   • Root Directory  (Réglages du service → onglet « Build & Deploy »)
   • Dockerfile Path

Si Root Directory contient encore « backend » (réglage d'une tentative
précédente), Render cherche alors « backend/Dockerfile » et ne trouve pas
le Dockerfile de la racine → même erreur qu'avant.

AVEC LE PAQUET A (teebo-COMPLET) :
   Root Directory      : laissez VIDE
   Dockerfile Path     : Dockerfile
   (ou ./Dockerfile)

AVEC LE PAQUET B (teebo-SERVEUR-backend) :
   identique, tout est à la racine de l'archive.

Puis : Manual Deploy → « Clear build cache & deploy ».

6) DANS RENDER
---------------------------------------------------------------------
  a. Base : le service PostgreSQL teebo-db doit exister (Blueprint
     render.yaml le crée). Sinon : New → PostgreSQL → nom « teebo »,
     région Frankfurt.
  b. Variables à saisir (Environment) :
        DATABASE_URL     = Internal Database URL de votre base
        TEEBO_ADMIN_PASSWORD = votre mot de passe administrateur
     Les autres (PUBLIC_SITE_URL, TEEBO_WHATSAPP, etc.) sont déjà dans
     render.yaml.
  c. Deploy, puis surveillez les journaux. Vous devez voir, dans cet ordre :
        teebo API en écoute sur 0.0.0.0:3000
        Dossier des migrations : /app/db
        Schéma appliqué : schema.sql … schema_v33.sql
        Migration terminée.
  d. Ouvrez /ready puis /healthz.
